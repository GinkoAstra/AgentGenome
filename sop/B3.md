# B3 execution boundary

`Registry` exposes six fixed local capabilities: profile, customer normalization,
deduplication, customer summary, lossless JSON input preparation, and its parameterized fixed variant. Definitions select registry IDs and supply
validated values; they cannot supply executable source. Each capability writes
fresh filenames under its operation directory. Both capability and checker
versions bind `capabilities.py`, `common.py`, `contracts.py`, `input_preparation.py`, and `parameter_forms.py`; changed dependencies invalidate
an accepted definition through the runtime's comparison.

CSV inputs use UTF-8, exactly the declared ordered columns, LF line endings and
a final LF. Identifiers must be nonempty (customers after trimming). Revision
and amount lexemes are signed or unsigned ASCII integers; decimal, exponential,
Unicode digit, blank and padded numeric fields are rejected. Integer magnitude
is not truncated and amount calculation never uses floats. Output integers use
canonical decimal notation. Customer IDs are trimmed; order IDs are unchanged.
The supplied requirements do not add nonnegative amount or revision constraints.

`orders.clean` and `orders.report` acceptance independently reread original input
and implement their own selection and totals, without calling producer parsing,
selection or summary helpers. They compare every cleaned row, customer row,
ordering and quality statistic; equal totals alone cannot pass. Highest revision
conflicts and customer differences across any revisions reject. Identical highest
ties and full refunds pass. Expected fixture files are used only by tests.

`ScriptedAgent` / `ScriptedPlanner` are explicitly labelled protocol test doubles.
`PiAgent` / `PiPlanner` start installed, matching Pi agent-core/pi-ai/coding-agent 0.80.6 or 0.87.1 through
`pi_worker.mjs`. Execution agents receive context/handoff and, when enabled by the host, a capability proxy.
That proxy sends strict inputs through bounded JSONL to B2 for per-call grant,
ownership, semantic-role and budget checks. It exposes logical handles, no native
read/write, shell, code evaluation or network business tool. Author, independent
semantic reviewer and planner only receive context/handoff. Provider transport reads trusted local Pi settings and
authentication separately; those values never enter the prompt or evidence.
This is a restricted tool interface, not an OS-level sandbox for the trusted
Node/Pi installation. No untrusted model code is ever evaluated by the worker.

Provider/model default to Pi settings, with explicit constructor settings or
`SOP_PI_PROVIDER` / `SOP_PI_MODEL` overrides. Each request has bounded model turns,
tokens and wall time; failure never falls back to a scripted result. Public
`max_model_calls_per_request` permits the parent to reserve the entire possible
model budget before dispatch. `last_evidence` records actual provider, model,
Pi version, call count, usage and safe errors, without credentials or raw transport
messages. Only D04 handoff is returned; B2 owns every state transition.

Reproduce unit checks:

```sh
python3 -m unittest discover -s tests/recursive_sop -p test_execution.py -v
node --test tests/recursive_sop/pi_worker.test.mjs
```

The Node tests execute the installed Pi loop with an explicitly scripted model
transport; the Python integration test exercises actual runtime contexts through
a mocked transport. These are program/protocol checks, not real-model samples.

Historical local real-provider probes recorded that configured `bailian/glm-5.2`
returned HTTP 403 before yielding tokens on 2026-09-28.
Those attempts validate genuine transport failure reporting, not successful
model behavior, natural-language authoring quality or algorithmic benefit.


JSON input preparation accepts an array of exact five-field records, string IDs
and integer revisions/amounts (booleans/floats/guessed coercions rejected). It
preserves original record order, whitespace and numeric values. The independent
preparation checker compares original JSON, all prepared CSV fields and explicit
mapping/provenance; even compensating amount edits or early deduplication reject.
A rejected preparation candidate is never made available to a consumer.

Task-internal tool operations use the same durable intent/candidate/check/commit
protocol as fixed nodes. Identical committed requests reuse receipts, and saved
candidates recover without re-execution. Unknown effects stop; tool calls cannot
change rule, code, checks or authority. Final Pi output must consist of current
owned handles and still passes the independent task checker. Direct tool output
commit does not advance graph pc. See PROTOCOL.md for exact callback fields.

The production Python→Node→installed Pi→host callback chain is also tested using
synthetic HTTP responses with a temporary fake provider configuration. It is
program evidence, not a genuine language-model task result.


orders.prepare_configured is the fixed form-driven variant. Host validation binds
a complete identity column_map and an integer chunk_size within the run policy.
The serializer actually emits record batches of that size; source meaning,
record order and all prepared bytes remain identical. Its independent checker
validates parameter semantics and the original-to-prepared correspondence without
calling producer conversion helpers. Parameter correction is a B2 pre-execution
data proposal, never a replacement program or permission to consume bad output.


Pi compatibility is version-specific: discover the actual package above either the legacy CLI or dist/bundle/cli.js; reject unknown/mixed versions. For 0.87.1, use the public ModelRuntime/ModelRegistry with static offline initialization and finishTurn for immediate termination; retain the explicit 0.80.6 path. A second check before every stream call enforces request budget and ended authority. Model selection is explicit or comes from configured defaults; an absent model never triggers silent provider fallback. Provider failures expose only fixed category/HTTP-status metadata, never raw error bodies or auth values.
